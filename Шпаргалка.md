## 6. Готовый рассказ на 1–2 минуты (от первого лица)

«Моя работа — обработка текстовых файлов из выбранной папки, вариант В1.2. Нужно решить четыре задачи: найти самую частую пару подряд идущих символов, N самых длинных слов, файл с наибольшим числом общеупотребимых слов — то есть слов, которые есть в каждом файле хотя бы K раз, — и посчитать распределение знаков пунктуации по частоте. Регистр не учитывается.

Каждую задачу я сделал двумя способами по паттерну «Стратегия». Есть общий интерфейс `ITextFileSolver` с четырьмя методами и две реализации: `LinqSolver` — на цепочках LINQ, `NoLinqSolver` — только на циклах и коллекциях из `System.Collections.Generic`, без единого метода `System.Linq`. Форма работает только с интерфейсом; конкретный класс выбирается в одном месте, в методе `CreateSolver`, по значению выпадающего списка.

Методы не бросают исключений: файлы читаются в `try/catch`, а если задачу решить нельзя — возвращается `default` или пустая коллекция. Есть несколько тонких мест. Пары символов считаю внутри строки, границу строк не пересекаю. Слова беру все, а не уникальные, и сортирую устойчиво: в LINQ это гарантирует `OrderByDescending`, а в варианте без LINQ я вручную сравниваю индекс обнаружения слова, потому что `List.Sort` неустойчив. Для общеупотребимых слов суммирую личные счётчики каждого файла.

Интерфейс — WinForms: выбираю папку, решатель, задачу, параметры; расчёт идёт через `Task.Run`, поэтому окно не зависает. Результат показывается в таблице и на столбчатой диаграмме, которую я нарисовал сам в обработчике `Paint`, без сторонних библиотек. Правильность и одинаковость решателей проверяют 19 xUnit-тестов; сборка идёт без ошибок и предупреждений.»

## 7. Вопросы преподавателя и ответы

По переписке одногруппников: лабы и билеты сдаются раздельно, защита лабы занимает около 7 минут; вопросов именно по практике 4 там не встречалось, но экзаменационные вопросы про LINQ (9, 10, 11 «отложенное выполнение» — спрашивали 3 раза, 7 «делегаты» — 2 раза, 8 «лямбды») очень частые. Поэтому готовы ответы и на «общие», и на «по коду».

**1. Что такое LINQ и какие две формы записи?**
LINQ (Language Integrated Query) — встроенный в C# язык запросов к коллекциям (и не только: базы, XML). Две формы: **синтаксис запросов** (`from x in xs where ... select ...`) и **синтаксис методов** (`xs.Where(...).Select(...)`). Компилятор превращает первую форму во вторую. В работе везде использована вторая — цепочки методов расширения из `System.Linq` (`LinqSolver.cs:29-63`, `:81-97`).

**2. Что такое отложенное выполнение? Где оно проявляется?**
Большинство операций (`Where`, `Select`, `SelectMany`, `OrderBy`, `Distinct`, `Take`, …) лишь строят «рецепт» запроса и ничего не вычисляют. Вычисление происходит при перечислении: `foreach`, `ToList`, `First`, `Max`, `Sum`, `Count`, `All` — это **немедленные** операции. В `LinqSolver`: переменная `words` (`LinqSolver.cs:80-86`) — только запрос, реально он выполняется на `ToList()` (`:97`); `allWords` (`:121-125`) ленивый и выполняется вместе с `commonWords` на `ToList()` (`:134`). А `perFileCounts` сразу сохранён `ToList()` (`:118`) — иначе каждое обращение перечитывало бы файлы.
Пример с изменением коллекции:

```csharp
var list = new List<int> { 1, 2, 3 };
var q = list.Where(x => x > 1);      // запрос ещё не выполнялся
list.Add(4);                          // меняем источник ПОСЛЕ создания запроса
Console.WriteLine(string.Join(",", q));   // 2,3,4  — 4 попало, потому что запрос выполнился только сейчас
var snapshot = list.Where(x => x > 1).ToList(); // немедленно: [2,3,4]
list.Add(5);                          // snapshot остался [2,3,4]; заново созданный запрос дал бы 2,3,4,5
```

**3. Что такое захват внешних переменных (замыкание)?**
Лямбда может использовать переменные внешнего метода. В `LinqSolver.cs:132` лямбда `w => perFileCounts.All(d => d.TryGetValue(w, out int c) && c >= K)` берёт `perFileCounts` и параметр `K` снаружи. Захватывается **сама переменная**, а не копия значения; в сочетании с отложенным выполнением это значит, что если бы `K` изменили до `ToList()`, запрос использовал бы новое значение. У меня `K` не меняется, поэтому всё однозначно. Похожий захват — `line` внутри вложенной лямбды (`LinqSolver.cs:36-38`) и `solver`, `files` в `Task.Run(() => solver.GetX(files))` (`MainForm.cs:259`).

**4. Чем `LinqSolver` отличается от `NoLinqSolver`, и почему результаты одинаковы?**
Первый описывает *что* получить (декларативно), второй — *как* считать (циклы). Одинаковость обеспечена одинаковыми правилами: одинаковый нижний регистр (`ToLowerInvariant`), одинаковые разделители, при равенстве побеждает «первый по порядку» (устойчивая сортировка в LINQ ↔ строгое `>` и индекс обнаружения в ручной версии), одинаковые `default` для невозможных случаев. Это проверено тестами, которые гоняют оба решателя на одних данных (`SolversTests.cs:59`, `:66`).

**5. Паттерн «Стратегия» и SOLID: где O и D?**
«Стратегия» — семейство взаимозаменяемых алгоритмов за общим интерфейсом; клиент выбирает алгоритм во время выполнения (`CreateSolver`, `MainForm.cs:932`). **O (открыт для расширения, закрыт для изменения):** чтобы добавить третий способ (например, `ParallelLinqSolver`), достаточно нового класса с `ITextFileSolver`; методы `Show…Async` не меняются (правда, одну строку в `CreateSolver` и пункт списка всё же добавить нужно — честная оговорка). **D (зависимость от абстракций):** `ShowLongWordsAsync(ITextFileSolver solver, ...)` (`MainForm.cs:298`) зависит от интерфейса, а не от классов.

**6. Зачем интерфейс?**
Чтобы отделить «что делаем» от «как»: форма и тесты работают с контрактом, а не с конкретным классом; поэтому одни и те же тесты проверяют оба решателя (`Solvers()`), а решатель можно заменить в один клик.

**7. Почему методы не бросают исключений?**
Так требует задание: задача должна быть устойчивой к плохим данным. Файл читается в `try/catch` (`LinqSolver.cs:243-270`, `NoLinqSolver.cs:366-397`), проблемный файл считается пустым; плохие параметры (`null`, `N<=0`, `K<=0`, пустой массив) отсекаются в начале метода и дают `default`/пустой список. Проверено `SolversTests.cs:472`.

**8. Как разбиваются слова?**
`text.Split(delimiters, StringSplitOptions.RemoveEmptyEntries)` (`LinqSolver.cs:84`, `NoLinqSolver.cs:116`): режем по любому символу из `delimiters`, `RemoveEmptyEntries` выбрасывает пустые куски (два разделителя подряд). Затем `ToLowerInvariant()` — приведение к нижнему регистру по правилам инвариантной культуры (результат не зависит от языка ОС). `Split` — метод `string`, не LINQ, поэтому допустим и в `NoLinqSolver`. Форма добавляет к введённым разделителям `\n`, `\r`, `\t` (`MainForm.cs:486`).

**9. Почему `OrderByDescending` устойчив, а `List.Sort` — нет?**
Документация: `OrderBy/OrderByDescending` выполняют устойчивую сортировку — элементы с равным ключом сохраняют исходный порядок. `List<T>.Sort` использует интроспективную сортировку и **неустойчив**. Поэтому в `NoLinqSolver.GetLongWords` я храню индекс (`NoLinqSolver.cs:136`) и в компараторе при равной длине сравниваю индексы (`:146-150`).

**10. Как считается пара символов?**
Для каждой строки (в нижнем регистре) берём позиции `i = 0 … Length-2` и пару `(line[i], line[i+1])`. LINQ: `Enumerable.Range` + `Select` + `GroupBy` (`LinqSolver.cs:29-63`). Без LINQ: `for (i; i+1 < Length; i++)` и `Dictionary<(char,char),int>` (`NoLinqSolver.cs:40-58`). Кортеж — значимый тип, сравнивается по значению, поэтому пары из разных мест попадают под один ключ. Пробел тоже символ, поэтому пара может содержать пробел. Пар нет → `default` = `('\0','\0')`.

**11. Сложность алгоритмов.**
Пусть L — всего символов, W — всего слов, G — различных пар, U — различных слов, F — файлов, P — знаков в наборе.
- Пара символов: чтение и перебор O(L); подсчёт в словаре в среднем O(L); поиск максимума O(G). LINQ дополнительно хранит **все** пары в списке — память O(L), а вариант без LINQ хранит только различные пары — O(G); сортировка групп в LINQ — O(G log G).
- Длинные слова: сортировка O(W log W) в обоих (хватило бы и кучи O(W log N), но для учебной задачи сортировка проще).
- Общие слова: построение словарей O(W); проверка всех слов по всем файлам O(U · F); суммы O(F · C), где C — число общих слов.
- Пунктуация: перебор всех символов O(T) (проверка в `HashSet`/`Dictionary` в среднем O(1)) + сортировка O(P log P).

**12. Зачем `Task.Run` и `async/await` в UI? (вопрос 18: любой ли метод может быть async?)**
Чтение и обработка файлов может занять секунды; если делать это в UI-потоке, окно «зависнет». `Task.Run(() => solver.GetX(...))` (`MainForm.cs:259`) выполняет работу в пуле потоков, а `await` освобождает UI-поток до конца работы и потом продолжает код **в UI-потоке** — поэтому можно безопасно менять таблицу и график. **Не любой метод может быть `async`:** он должен возвращать `void`, `Task`, `Task<T>` (или `ValueTask`, `IAsyncEnumerable`), не может иметь параметры `ref/out`; `async void` допустим практически только для обработчиков событий — как `OnRunClick` (`MainForm.cs:146`), потому что его нельзя `await`-ить и исключения из него не перехватить снаружи (у меня они перехвачены внутри `try/catch`). Сами решатели остаются обычными синхронными методами (их контракт задан заданием), а асинхронность добавляет форма.

**13. Чем `Func`, `Action`, `Predicate` отличаются и где они здесь?**
Все — делегаты (типы, хранящие ссылку на метод). `Func<..., TResult>` возвращает значение, `Action<...>` — `void`, `Predicate<T>` — `bool` (то же, что `Func<T,bool>`). В коде: лямбды в LINQ — `Func` (`Select(w => w.ToLowerInvariant())`, `Where(...)` с условием — `Func<T,bool>`); сравнение в `Sort` — `Comparison<T>` (`NoLinqSolver.cs:146`, `:342`); `SelectMany(TryReadLines)` — метод, переданный как делегат (группа методов); `Task.Run(() => ...)` принимает `Func<TResult>`/`Action`; события (`Click += OnRunClick`) — делегат `EventHandler` (`MainForm.cs:95-105`).

**14. Что такое `ValueTuple`?**
Значимый тип (структура) — кортеж из нескольких значений. `ValueTuple<char,char>` то же, что `(char, char)`; поля `Item1`, `Item2` (в LINQ-коде у кортежей ещё и именованные элементы: `First`/`Second`, `File`/`Total`, `Char`/`Index`). Сравнивается по значению (поэтому подходит как ключ словаря и для `GroupBy`), `default` даёт нулевые значения — `('\0','\0')` и `(null, 0)`, это и есть «ничего не найдено» (`ITextFileSolver.cs:21`, `:32`).

**15. Для чего юнит-тесты?**
Проверять, что решатели правильные и **одинаковые**, и защищать от поломок при изменениях (регрессия). Каждый тест: подготовка (временные файлы в `CreateFile`), действие (вызов решателя), проверка (`Assert`); xUnit создаёт объект класса на каждый тест, `Dispose` чистит временную папку (`SolversTests.cs:12-39`). Граничные случаи: пустой массив, несуществующий файл, `N<=0`, `K<=0`, нет общих слов, нет пар.

**Быстрые ответы на возможные «подкаты»:**
- *Почему `Split` можно использовать в решателе без LINQ?* Это метод класса `string`, а не метод расширения `System.Linq`. Так же `List.Sort`, `Dictionary`, `File.ReadAllText`.
- *Гарантирует ли `Dictionary` порядок вставки?* Официально порядок не гарантирован, на практике без удалений `foreach` идёт в порядке вставки — на этом построено допущение, разрешённое заданием («упорядоченность как порядок вставки»).
- *Что будет при равных частотах у пар?* Побеждает пара, которая появилась раньше (в LINQ — устойчивая сортировка групп, в ручной версии — строгое `>` по порядку первого появления).
- *Почему в `NoLinqSolver` нет `using System.Linq`?* Чтобы случайно не вызвать LINQ; implicit usings подключают только `System`, `System.IO`, `System.Collections.Generic` и т.п.
- *Как убедились, что нет LINQ?* Нет `using System.Linq;` и вызовов `Select/Where/...` — можно показать поиском по файлу.

## Приложение. Теория LINQ, ужато

- **LINQ** — запросы к коллекциям средствами C#: методы расширения `System.Linq` над `IEnumerable<T>` (`Where`, `Select`, `SelectMany`, `GroupBy`, `OrderBy/OrderByDescending/ThenBy`, `Take`, `Distinct`, `All`, `Sum`, `Max`, `First`, `ToList`, …).
- **Отложенное выполнение:** запрос — это «рецепт»; выполняется при перечислении (`foreach`, `ToList`, `First`, `Count`, …). `ToList()` **материализует** результат (сохраняет в памяти).
- **`Select`** — преобразовать каждый элемент (map); **`Where`** — отфильтровать (filter); **`SelectMany`** — «сплющить» набор наборов в одну последовательность; **`GroupBy`** — сгруппировать по ключу (`IGrouping<K,T>`, `Key` — ключ группы); **`Take(N)`** — первые N; **`Distinct`** — убрать повторы.
- **Сортировка:** `OrderBy` — по возрастанию, `OrderByDescending` — по убыванию, `ThenBy` — вторичный ключ. Устойчива: элементы с равным ключом сохраняют исходный порядок.
- **Разбиение на слова:** `string.Split(delimiters, RemoveEmptyEntries)` — не LINQ; регистр убираем `ToLowerInvariant()`.
- **Без LINQ** можно использовать всё, что не из `System.Linq`: `Dictionary`, `List`, `HashSet`, `List.Sort(Comparison<T>)`, `Split`, `File.*`.
- **Ошибки:** методы решателей не бросают исключений; вместо этого — `default` или пустая коллекция; файлы читаются через `try/catch`.
- **Тесты:** xUnit (`[Fact]`, `Assert`, `Record.Exception`); почти каждый тест гоняет оба решателя в `foreach (var solver in Solvers())`.
