# Практическая работа №4. Технология LINQ для обработки файлов

Вариант: **В1.2**

## Формулировка задания

Требуется реализовать обработку текстовых файлов в заданной пользователем папке.
Каждая вычислительная задача изолирована — не зависит от других задач, полностью
определяется входными аргументами и не должна порождать исключений: если задачу
решить невозможно (нет файлов, пустой результат, некорректные параметры), метод
должен вернуть значение по умолчанию (`default`), а не бросать исключение.

Каждая задача должна быть реализована **двумя способами**:

- с использованием методов `System.Linq` (`Where`, `Select`, `GroupBy`, `OrderBy` и т.п.);
- **без единого метода из `System.Linq`** — только явные циклы (`for`/`foreach`) и
  структуры данных из `System.Collections.Generic`.

Для этого используется паттерн проектирования **«Стратегия»**: общий интерфейс
`ITextFileSolver` с четырьмя вычислительными методами и два класса-решателя,
реализующие этот интерфейс, — `LinqSolver` и `NoLinqSolver`. Решатели могут иметь
дополнительные приватные методы и поля, но не должны содержать консольный
ввод-вывод — вся логика чтения файлов инкапсулирована внутри решателя, а
представление результата — задача UI-слоя.

Решение состоит из двух проектов:

1. **Библиотека** `Lab4.Solvers` (`namespace Lab4.Solvers`) — интерфейс
   `ITextFileSolver` и классы `LinqSolver`, `NoLinqSolver`.
2. **WinForms-приложение** `Lab4.UI` (`namespace Lab4.UI`) — позволяет выбрать
   папку с файлами, задать параметры (N, K, разделители, знаки пунктуации),
   выбрать решатель (LINQ / без LINQ) и задачу, и показывает результат в
   табличном виде (`DataGridView`) и в виде столбчатой диаграммы.

## Мой вариант — В1.2

```csharp
namespace Lab4.Solvers;

public interface ITextFileSolver
{
    ValueTuple<char, char> GetPopularCharPair(string[] files);
    IList<string> GetLongWords(string[] files, char[] delimiters, int N);
    ValueTuple<string,int> GetFileWithManyCommonWords(string[] files, char[] delimiters, int K);
    IDictionary<char, int> GetPunctuationDistribution(string[] files, char[] punctuations);
}
```

Обработка всех методов ведётся **без учёта регистра** (буквы приводятся к нижнему
регистру перед сравнением/подсчётом). `files` — массив абсолютных путей к
`.txt`-файлам, `delimiters` — символы-разделители слов.

### 1. `GetPopularCharPair(files)`

Находит самую часто встречающуюся пару **подряд идущих символов** по всем файлам.
Своими словами: берём содержимое всех файлов, и для каждой строки каждого файла
считаем частоту пар соседних символов (первый и второй символ пары стоят рядом в
тексте), затем находим пару с максимальной суммарной частотой по всем файлам.

**Принятые решения по неоднозначностям:**

- Пары считаются **только внутри одной строки**: символ конца одной строки и
  первый символ следующей строки в пару не объединяются (это явно не указано
  в ТЗ, но является наиболее логичной трактовкой понятия «строка/файл» и
  проверено отдельным тестом `GetPopularCharPair_DoesNotCrossLineBoundary`).
- Учитываются **все** символы строки — буквы, пробелы, знаки препинания
  (ТЗ не ограничивает набор символов).
- Если файлов нет, все файлы пустые или подряд идущих пар символов вообще нет
  (например, каждая строка состоит из одного символа) — возвращается
  `default` — `('\0', '\0')`.
- При равенстве частот нескольких пар побеждает пара, встретившаяся раньше при
  последовательном сканировании файлов (детерминированный, но не заданный явно
  в ТЗ порядок — оба решателя используют одинаковое правило, что проверено
  тестами).

### 2. `GetLongWords(files, delimiters, N)`

Возвращает **N самых длинных слов** по всем файлам. Слова получаются разбиением
содержимого каждого файла по символам `delimiters` (`string.Split` с
`RemoveEmptyEntries`, пустые токены игнорируются).

**Принятые решения по неоднозначностям:**

- Берутся **все вхождения** слов (а не только уникальные) по всем файлам —
  если слово повторяется, оно может занять несколько позиций в итоговом
  списке.
- Сортировка по убыванию длины — **устойчивая**: при равной длине слова
  сохраняют исходный порядок обнаружения (порядок файлов в массиве `files`,
  затем порядок слов внутри файла). Для `LinqSolver` это гарантируется
  документированной стабильностью `OrderByDescending`; для `NoLinqSolver` —
  ручной сортировкой с явным тай-брейком по индексу обнаружения слова.
- Если `N <= 0` или слов нет вообще — возвращается **пустой список**
  (не `null`).

### 3. `GetFileWithManyCommonWords(files, delimiters, K)`

Возвращает файл с наибольшим количеством вхождений **общеупотребимых** слов и
само это количество.

**Принятые решения по неоднозначностям (по заданию из практической работы):**

1. Сначала определяется множество общеупотребимых слов: слово считается
   общеупотребимым, если оно встречается **в каждом из файлов** не менее `K`
   раз (без учёта регистра).
2. Затем для каждого файла считается **суммарное количество вхождений**
   общеупотребимых слов именно в этом файле — то есть используется
   индивидуальный (per-file) счётчик каждого общего слова, а не просто
   количество различных общих слов.
3. Возвращается файл с максимальной суммой и сама эта сумма.
4. Если общеупотребимых слов нет, файлов нет или `K <= 0` — возвращается
   `default`: `(null, 0)`.
5. При равенстве сумм у нескольких файлов побеждает файл, который идёт раньше
   в массиве `files` (строгое сравнение `>` при переборе).

### 4. `GetPunctuationDistribution(files, punctuations)`

Считает суммарную (по всем файлам) частоту встречаемости каждого символа из
`punctuations`.

**Принятые решения по неоднозначностям:**

- В результирующий словарь включаются **все** символы из `punctuations`, даже
  с нулевой частотой встречаемости.
- Повторяющиеся символы во входном массиве `punctuations` схлопываются в один
  ключ словаря (иначе `Dictionary` не смог бы содержать дублирующиеся ключи);
  при этом запоминается позиция **первого** вхождения символа в массиве для
  тай-брейка.
- Символы добавляются в словарь **в порядке возрастания частоты**, а при
  равной частоте — в порядке их первого появления в исходном массиве
  `punctuations`. Поскольку `Dictionary<char,int>` в реализации .NET
  сохраняет порядок вставки на практике, `foreach` по результату отражает
  требуемую упорядоченность по возрастанию — это прямо оговорено в задании
  как достаточное решение.

## Реализация

### Архитектура

Решение состоит из трёх проектов, объединённых файлом решения
`КостинДА_4пр.slnx` (актуальный SDK `10.0.201` по умолчанию создаёт решение в
новом XML-формате `.slnx` вместо классического `.sln`; команды `dotnet build`,
`dotnet test`, `dotnet sln` работают с ним идентично):

- **`Lab4.Solvers`** (`net10.0`, библиотека классов) — интерфейс
  `ITextFileSolver` и два класса-стратегии `LinqSolver` / `NoLinqSolver`.
  Каждый решатель самостоятельно и безопасно читает файлы (обёртки
  `TryReadAllText`/`TryReadLines` с `try/catch`, чтобы отсутствующий или
  недоступный файл не приводил к исключению — такой файл просто
  пропускается, как будто он пуст).
- **`Lab4.UI`** (`net10.0-windows`, WinForms) — ссылается на `Lab4.Solvers`.
  `MainForm` позволяет выбрать папку (`FolderBrowserDialog`), решатель
  (`ComboBox`: LINQ / без LINQ), задачу из списка четырёх задач варианта,
  задать `N`, `K`, набор разделителей и набор знаков пунктуации. Файлы
  собираются как `*.txt` из выбранной папки (без вложенных подпапок).
  Результат выводится в `DataGridView` (табличное представление) и
  дополнительно отрисовывается вручную (`Graphics.FillRectangle`/`DrawString`
  в обработчике `Paint` для `PictureBox`, без сторонних библиотек графиков) в
  виде столбчатой диаграммы с подписями осей и всплывающими подсказками
  (`ToolTip`) при наведении на столбец. Тяжёлые вычисления выполняются через
  `Task.Run`, чтобы не блокировать поток интерфейса.
- **`Lab4.Tests`** (`net10.0`, xUnit) — 19 тестов, проверяющих:
  - что `LinqSolver` и `NoLinqSolver` дают **идентичный результат** на одних
    и тех же входных данных для всех 4 методов (тесты
    `*_BothSolvers_ReturnSameResult`, а также общий цикл `foreach (var solver
    in Solvers())` почти во всех тестах — каждая проверка выполняется
    поочерёдно для обоих решателей с одинаковыми входными данными и
    одинаковыми ожиданиями);
  - корректность граничных случаев (пустой массив файлов, несуществующий
    файл, `N<=0`, `K<=0`, отсутствие общеупотребимых слов, отсутствие
    подряд идущих пар символов) — во всех случаях методы не бросают
    исключений и возвращают `default`/пустую коллекцию;
  - что пары символов не «перепрыгивают» через границу строк;
  - устойчивость сортировки в `GetLongWords` при равных длинах слов;
  - упорядоченность результата `GetPunctuationDistribution` по возрастанию
    частоты и включение в словарь всех символов, даже с нулевой частотой.

  Идентичность результатов двух решателей проверялась именно через
  юнит-тесты (`dotnet test`), а не вручную — каждый тест, где это уместно,
  прогоняет один и тот же сценарий на обоих экземплярах `ITextFileSolver`
  через фабрику `Solvers()`.

### Паттерн «Стратегия»

`ITextFileSolver` — общий интерфейс стратегии. `LinqSolver` и `NoLinqSolver` —
взаимозаменяемые конкретные стратегии, реализующие одну и ту же задачу разными
алгоритмическими средствами (с LINQ и без). UI (`MainForm.CreateSolver()`)
в момент выполнения выбирает нужную стратегию по значению `ComboBox`, ничего не
зная о внутренней реализации — это и есть суть паттерна.

```powershell
# Собрать всё решение
dotnet build "КостинДА_4пр.slnx"

# Запустить UI
dotnet run --project Lab4.UI/Lab4.UI.csproj

# Прогнать тесты
dotnet test Lab4.Tests/Lab4.Tests.csproj
```

Либо через `.vscode/launch.json` — конфигурации «Lab4.UI Run (workspace root)»
и «Lab4.Tests Run».
